# Wave 5 / Stage 2 / Task 2 — Migration v8 and schema plumbing

## Objective

Move the database from v7 to v8: create `cuenta` and `transferencia`, rebuild `movimiento` with
`cuenta_id` and `medio_pago` and without `monto_moneda`, and make the movimiento view expose the
account's currency, so `cuenta.moneda` is the single owner of a movimiento's currency. Keep the whole
build and every existing behaviour green: this task rewrites each query and construction site that
the schema change breaks, and nothing more.

## Contracts

```kotlin
data class Movimiento(/* existing fields */, val cuentaId: String, val medio: MedioPago, /* etiquetaIds */)
data class MovimientoChanges(/* existing fields */, val cuentaId: String, val medio: MedioPago)
```

- `monto: Money` stays: its currency is now read from the view's `monto_moneda` (= `cuenta.moneda`).
  `insertRow` no longer writes a currency; it writes `cuenta_id` and `medio_pago`.
- No default parameter values on the production types. Until Stage 4 the existing creation path takes
  `defaultSelection(primary, MedioPago.EFECTIVO)` and builds the draft's money in the selected
  account's currency; editing keeps the stored `cuentaId`/`medio`. This is real behaviour, not a
  placeholder. Invariant checks are task3's.

```kotlin
data class CuentaSelection(val cuentaId: String, val medio: MedioPago) // core.model
// MovimientoRepository
/** Null only when [medio] is given and no live active account is compatible with it. */
suspend fun defaultSelection(primary: Moneda, medio: MedioPago? = null): DataOutcome<CuentaSelection?>
```

`defaultSelection` is the single producer of the README fallback order
([Entry and selection](../../README.md#entry-and-selection)); one SQL read, no preference.

## Exact rules

- DDL target: README [Schema plan](../../README.md#schema-plan); `cuenta` and `transferencia` carry the
  same `updated_at`/`deleted_at` definitions Stage 1 gave the other roots.
- Backfill one `EFECTIVO` account per distinct currency of **all** movimiento rows, tombstones
  included (a revived row must still reference an account): ID `cuenta_efectivo_<lower(moneda)>`,
  `nombre` "Efectivo", `saldo_inicial_minor` 0, `created_at` = the earliest `created_at` of that
  currency, `updated_at` = `ChangeStamp.SEED` literal. Every movimiento gets that ID and `EFECTIVO`;
  its `updated_at`/`deleted_at` are copied unchanged (a migration is not a user change).
- The rebuilt table, view and indexes must equal a fresh install (`verifyMigrations`). The view keeps
  its name and columns plus `cuenta_id`, `medio_pago`, and `cuenta.moneda AS monto_moneda`, joined
  through `cuenta` (live filter unchanged from Stage 1).
- Queries that read the table directly filter currency through `cuenta`; their results, ordering and
  existing index comments must stay true. Re-run the existing `EXPLAIN QUERY PLAN` assertions in
  `HistoryRepositoryTest`/`SearchRepositoryTest`: adjust indexes if a plan regresses, never the
  assertion. Add the live partial index `movimiento(cuenta_id)`.
- Transfers have no rows yet; their indexes (both account columns, `fecha`) are created here.
- Fresh install: after preferences, the bootstrapper inserts `cuenta_efectivo_<primary>` with the
  localized cash name and `ChangeStamp.SEED` **only when `countLiveCuentas` is 0**; a restart or a later
  primary-currency change inserts nothing. `changeClock.prepare` still runs last.
